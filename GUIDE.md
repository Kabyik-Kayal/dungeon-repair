# Guide

This is the long explanation of the project — what it does, how it works, why
it's built this way, and what to read if you want to go deeper on any of it.

The other files here have narrower jobs. The [README](README.md) is the short
pitch and the numbers. The [changelog](CHANGELOG.md) is the diary: what we
tried, in order, and what the evidence said. [REPRODUCE.md](REPRODUCE.md) is
the list of commands. [docs/DATA_NOTES.md](docs/DATA_NOTES.md) covers the
quirks of the dataset. This file is the one that explains how the thing
actually works.

---

## 1. The problem

Say you're making a game where levels are generated by code rather than drawn
by hand. A dungeon crawler, a roguelike, something Zelda-shaped. The generator
lays out rooms, scatters keys around, and locks some of the doors.

Sometimes it produces a dungeon nobody can finish.

The classic version is that the key for a door ends up *behind* that door. But
there are others: a corridor gets dropped and a whole wing is cut off, or three
locked doors sit on the only route forward and the generator only placed two
keys.

### Why this is harder to detect than it sounds

The obvious check is "can I walk from the start to the end?" That works for a
maze. It falls apart the moment keys enter the picture, because **keys get used
up**.

Think about what that means. You're standing in a room holding one key, and
there are two locked doors. Whether you can finish the level depends on which
one you open. A room that's reachable if you save your key is unreachable if
you spent it ten rooms ago on the wrong door.

So the real question isn't "is there a path?" It's "is there *some order* of
picking up keys and spending them that gets me to the end?" That's a much
bigger question, and it's why a simple connectivity check can happily approve a
dungeon that can't be completed.

### What people do about it today

Two things, and neither is good.

**Play every level by hand.** Reliable, and hopeless as soon as you're
generating more levels than a person can sit through.

**Throw it away and roll again.** Generate a dungeon, check it, and if it fails,
bin it and generate another. This scales fine and it's what most teams actually
do. The problem is that you lose everything — including all the parts that were
good — and you learn nothing about what went wrong.

### What we set out to build

Something that could do two things: prove whether a level can be finished, and
when it can't, fix it the way the person who designed it would have fixed it.
Repair the level, don't replace it.

Then we measured, and found out that half of that goal was already solved.

## 2. The thing we got wrong, which turned out to be the project

The original plan was the obvious one. Point an AI agent at a broken level, let
it work out what's wrong, propose a fix, check the fix, try again if it fails.

Before building any of that, we checked whether it was even necessary. We wrote
a script that tries every possible small change — move a key, add a key, unlock
a door, add a corridor — and asks the solver whether each one works.

**It fixed every broken level we gave it. In under a second. For no money at
all.**

That's worth sitting with. If a plain script fixes 100% of cases instantly and
for free, then "make this level completable" is not a job for an AI agent. Any
model you point at it is competing with something faster, cheaper, and provably
correct, and losing on all three counts.

But the same experiment showed us something more interesting. When we counted
how many different fixes worked, the answer was: **loads**. A typical broken
level has around 60 valid fixes. Some have as many as 612.

And when we looked at *which* fix the script picked, it was usually terrible.
Faced with a missing corridor, it would happily connect two rooms on opposite
ends of the dungeon. Technically the level is now completable. In practice
you've just installed a teleporter through the back wall, and no designer would
ship it.

So the script scores 100% on "is it completable" and 34% on "is it the fix the
designer wanted."

That flips the whole design around:

> **Being correct is free. Having taste is not.**
>
> The solver decides what's correct. A script generates every correct option.
> The agent's only job is to pick a good one and explain why.

There's a nice side effect. Since the agent can only choose from options that
have already been proven to work, **it is structurally incapable of shipping a
broken level**. It never spends any effort on correctness, because correctness
was handled before it was asked. It spends everything on the one question the
solver can't answer: which of these sixty correct answers is the *right* one?

## 3. How it fits together

```
   the dungeon files
          │
          │  read the graph            check if it's completable
          ▼                                      │
       a Level ─────────────────────────────────►│
          │                                      ▼
          │  break it on purpose            "no, and here's why"
          ▼                                      │
   a Case: broken level                          │
   + the change that broke it                    │
          │                                      │
          │  try every small fix                 │
          └──► keep the ones that work ──────────┤
                        │                        │
                        ▼                        ▼
              ~60 verified options          the diagnosis
                        └───────┬────────────────┘
                                ▼
                            the agent
                  looks, compares, picks, explains
                                │
                        a human says yes
                                ▼
                    the repaired level + a full
                    record of how it got there
```

Everything flows one direction, and the important property is that nothing
after the solver can produce a level the solver hasn't approved.

## 4. A tour of the code

Everything lives in `src/dungeon_repair/`. Here's what each piece does and the
one thing about it worth knowing.

**`level.py` — what a dungeon *is*.**
A level is rooms and the passages between them. Rooms can contain things (the
start, the exit, a key, the boss key). Passages can require things (a key, the
boss key, an item).

Two details matter. First, passages point one way. That sounds like overkill
until you notice the real dungeons have doors that are open going one direction
and locked coming back. If we stored doors as simple two-way connections we'd
silently throw that away.

Second, levels never change in place. Every edit produces a brand new level.
That sounds wasteful, but the fix-generator tries thousands of speculative edits
per level, and if any of them accidentally modified the original we'd get bugs
that are almost impossible to track down.

**`vglc.py` — reading the dungeon files.**
The dataset stores each dungeon as a graph file. This turns those into levels.
It's short, and it contains the nastiest trap in the project.

The obvious way to find a room in the file is to look for `something [label="..."]`.
The problem is that a *connection* looks like `7 -> 8 [label="k"]`, which ends
in exactly the same shape. So the pattern matches the `8` too, and quietly
overwrites room 8's contents with the label belonging to the corridor. Nothing
crashes. You just get a dungeon that's subtly wrong. The fix is to blank out all
the connection lines before looking for rooms.

**`solver.py` — the referee.** Big enough that it gets [its own section](#5-the-solver).

**`edits.py` — the four things you're allowed to change.**
Move a key. Add a key. Unlock a door. Add a corridor. That's the whole
vocabulary.

One subtlety: unlocking the door between rooms 3 and 5 is the same as unlocking
the door between 5 and 3, so we sort the two room numbers to make those count as
one answer. But *moving* a key from room 3 to room 5 is not the same as moving
it from 5 to 3, so we deliberately don't sort those. Getting this wrong cost us
a wrong published number once — it's Stage 8 in the changelog.

The reason there's one shared vocabulary is important: it's what lets us express
"the change that broke this level" and "the fix the agent chose" in the same
terms, which is the whole basis of the measurement.

**`corrupt.py` — breaking levels on purpose.**
This takes a working dungeon and applies exactly one change to break it, while
writing down what that change was:

| what we break | how | the fix we're hoping for |
|---|---|---|
| a misplaced key | move a key somewhere it shouldn't be | move it back |
| a missing corridor | delete a connection | put it back |
| a wrong lock | lock a door that should be open | unlock it |

Two rules keep the test cases meaningful. We only keep a broken level if the
solver confirms it's genuinely unfinishable — that way every case sits on the
critical path rather than damaging some irrelevant side room. And we never move
a key into a room that already has one, because you can't undo that with a
single move, which would leave the case with no correct answer.

We also cycle evenly through the three kinds of damage. If you just pick
randomly, you end up with far too many deleted corridors, because deleting a
corridor breaks a dungeon much more often than moving a key does. That would
bury the misplaced-key case, which is the one the whole project is about.

**`candidates.py` — generating every fix that works.**
Runs through the entire vocabulary of possible edits and keeps the ones the
solver approves.

The order it tries them in is deliberate: unlock a door, then move a key, then
add a key, then add a corridor. Roughly least-destructive first. Unlocking or
moving leaves the floor plan alone; adding a key changes the difficulty; adding
a corridor rewrites the map. We chose this order to make the simple script we're
competing against as strong as possible. It later turned out to bias the agent
too, which is [section 9](#9-what-actually-happened).

**`topology.py` — measuring shape.**
How many doors apart are two rooms, ignoring locks. And how much of the original
dungeon survives a repair, scored 0 to 1 — a single small fix scores about 0.97,
a regenerated dungeon about 0.03.

**`agent/` — the part being tested.** [Section 6](#6-the-agent).

**`baselines/` — the three things we compare against.**
Rolling a fresh dungeon until one works. Asking a model once with no tools and
no solver. And the simple script that takes the first fix that works.

**`llm.py` — talking to the model.**
One small wrapper, so there's exactly one place that makes model calls and one
place that counts what they cost. A few choices worth flagging:

We don't set `temperature`. Current reasoning models reject that setting
outright. This has a real consequence for the results, covered in section 9:
**the agent gives different answers to identical questions, and we can't turn
that off.**

Prices come from the model library's own price list rather than a table we typed
in ourselves, so they can't drift out of date. If it doesn't know a model, we
report the cost as unknown rather than guessing.

Costs are calculated from actual token counts, which matters because some models
charge more for very long inputs. And every request has a 2-minute time limit
and retries, because results only get written once every case finishes — a
single request hanging forever would throw away a completed run.

**`trace.py` — recording what happened.**
Every model call, every tool call, every rejection, every retry gets written to
a file as it happens rather than reconstructed afterwards. These recordings are
one of the things we have to hand in, and there's a command that turns one into
readable text.

**`route.py` — the facts the candidate list already implies.**
Sometimes the list of verified fixes gives the answer away, and nobody says so
out loud. If moving a key repairs the level *and* there's exactly one door the
solver will let you unlock, then a lock was invented that shouldn't exist, and
there's only one door it can be. This module spots that shape. It doesn't answer
— it hands the observation to the agent as a line in the diagnosis. Section 9
covers why that distinction turned out to matter more than we expected.

**`memory.py` — what the designers usually do.**
Motifs measured across the *other* dungeons: keys sit with enemies three times
in four against a base rate of half, they're dead ends more often than chance,
they almost never share a room with the key item. The dungeon being repaired is
always held out, which is the entire difference between evidence and cheating,
and there's a test that pins it.

The honest headline on this module is that the motifs are real and too weak to
act on. Every number it prints comes with its lift attached for exactly that
reason.

**`metrics.py`, `runner.py`, `cli.py` — scoring, running, and the command line.**
The runner catches errors per level, so one bad case gets recorded as a failure
instead of killing the whole run.

## 5. The solver

Everything else trusts this component, so it's worth understanding properly.

### Why the simple approach doesn't work

Because keys get used up. "Is there a path of open doors?" is the wrong
question. The right one is "does there exist some order of collecting and
spending keys that reaches the exit?"

### What it actually tracks

At any moment the solver is tracking four things:

- which room you're standing in
- which keys you've picked up
- which doors you've already opened
- whether you have the special items (the boss key, the key item, which
  switches you've hit)

"How many keys do I have right now" is then just keys picked up minus doors
opened.

**Why "which doors you've opened" has to be in there.** Keys are
interchangeable and they're consumed. If you only track *how many* keys someone
has, you can't tell the difference between "two keys, spent none" and "three
keys, spent one on the wrong door." Those lead to completely different outcomes,
and a solver that can't distinguish them will confidently approve levels that
can't be finished.

**Why we store these as bit patterns.** The straightforward approach is to keep
a list of everything collected. It's correct, and it's far too slow — it hangs
on the biggest dungeons. Storing them as bit patterns instead (one bit per key,
one bit per lockable door — there are rarely more than a dozen of each) makes
every dungeon in the collection finish in well under a second. The whole set of
38 checks in half a second.

### Two rules we had to discover by experiment

Neither of these was written down anywhere. We worked them out by trying both
readings and seeing which one matched reality.

**"Soft locked" doors are actually passable.** The dataset marks some doors
"soft locked," which sounds like it should block you. But 101 doors are marked
that way in *both* directions — which would mean a room is sealed off from
itself. That can't be right. And if you treat them as blocking, only 6 of the 38
real shipped dungeons come out completable, which is obviously wrong. Treated as
passable, 31 do. **That single decision is worth 25 dungeons.**

**Doors marked "impassable" really do block you.** Worth noting a confusing
detail of the data: the same letter means "start" when it's on a room and
"impassable" when it's on a door. What a symbol means depends on where it is.

### What it hands back

More than yes or no, because the agent needs something to reason about and a
designer needs an explanation:

- whether it's completable, and if not, why in plain language
- which rooms you can and can't reach
- which doors you can get to but never through, and what's stopping you
- an actual winning route, if one exists
- how much searching it took, so our performance claims can be checked

### The test that keeps it honest

31 of the 38 real dungeons come out completable. The other 7 aren't solver bugs
— they're mistakes in how the dataset was transcribed. One of them records a
single key against three locked doors that all sit on the only route forward,
which is impossible as written even though the real game obviously wasn't.

That number is locked into the test suite. If anyone changes the solver's rules
and the count moves, a test fails immediately.

Reproducing 31 real commercial dungeons *is* our correctness argument. There's
no other solver to check ourselves against — the closest published alternative
models a much simpler kind of level, with a single key and a single door.

## 6. The agent

### What it gets

A description of the broken dungeon and five tools — six if you switch on the
optional one below. It is specifically **not** given the job of finding a fix — the tool that lists fixes only ever returns
ones the solver has already approved.

| tool | what it answers |
|---|---|
| diagnose | why can't this be finished? |
| repair options | what fixes are available? (filterable, so it isn't drowned) |
| compare | how do these specific fixes differ? |
| room detail | what's in this room, what connects to it, how far is it? |
| submit | here's my answer and my reasoning |
| design rhythm | what do the same designers' other dungeons do with keys? (optional) |

The interesting one is **compare**. For each fix it reports how far apart the
rooms involved are, whether the map's shape changes, what happens to the number
of keys versus locks, what the new winning route looks like, and how many rooms
open up. This is the tool that carries actual design judgment.

It also deliberately accepts fixes that *don't* work, and just says so. If the
agent wants to test its own idea, it should be able to.

### The optional sixth tool

**design rhythm** is off unless you ask for it, and it's only offered on cases
where moving a key is even legal — the motifs are about where keys sit, so on a
dropped-corridor case it can't help and shouldn't be in the way.

It reports the habits with their strength attached: keys are in rooms with
enemies 76% of the time against a 53% base rate, which is a lift of 1.45. That
sounds like something. Section 9 explains why it turned out not to be.

### The safety catch

When the agent submits an answer, we check it against the approved list. If it
isn't on that list, the submission is refused and the refusal goes back to the
model as a message, and it tries again.

This is what makes it a verification loop rather than a suggestion box, and it's
tested directly: one test drives a model that only ever proposes broken fixes,
and confirms the run ends with no answer rather than a bad one.

### Asking a human

Nothing gets applied without someone approving it. When you run it interactively
it asks you; during automated evaluation it approves automatically, **and the
recording notes which of the two happened.**

### What we tell it

The instructions spend no words on being correct, because being correct is
already handled. Instead they describe what makes a repair *good*: keep it
local, restore rather than invent, don't quietly make the dungeon easier, don't
break the difficulty curve, make it look like it belongs.

And they ask for a specific kind of thinking: work backwards from the symptom to
the cause. What single mistake would produce *exactly* this failure, not just
some failure?

Section 9 covers how well that held up. Short version: less well than we hoped.

## 7. How we measured it, which was the hard part

### The problem with "which fix is better?"

It's a matter of opinion. Two fixes both work; which is nicer is a judgment
call. You can't put a number on a judgment call without a scoring rubric, and
people argue about rubrics. Asking another AI to judge would just import exactly
the subjectivity we're trying to measure.

### The trick

Take a level that works. Break it with a change we choose. Now we know the right
answer, because the right answer is undoing the change we just made.

"Did it recover what the designer intended?" becomes a plain factual question
with a yes or no answer.

This isn't an original idea, and it's worth naming where it comes from: it's
**mutation testing**, borrowed from software testing. Take something that works,
inject a deliberate fault, and see whether your tooling catches and fixes it.
There's a pointer to the literature in section 11.

### The test set

77 cases. 76 are real dungeons broken by our script, spread evenly across the
three kinds of damage. One is hand-built.

**The hand-built one** is the interesting case. It's a keep with a repeating
rhythm: before every locked gate there's a little alcove holding the key for
that gate. Three gates, three alcoves, same pattern each time. Then the third
key gets generated *behind* its own gate.

115 different fixes work. Ten of them involve moving the stranded key somewhere
useful. **Exactly one** puts it back in its alcove. Working out the *kind* of
bug is easy here. Making the right choice is not. That's the point of it.

### What we count

**Did it recover the intended fix?** The main number. Exact match.

**Is the level completable?** A floor, not an achievement. Anything with access
to the solver clears it automatically, so we report it mainly so nobody gets
credit for it.

**How much of the original survived?** Separates a small repair from bulldozing
the level and starting over.

**Time and money per level.**

Exact match is strict on purpose. A fix that's arguably just as good but
different scores zero. It's the only version of the measurement nobody can argue
with, and we pay for that strictness honestly — the agent's near miss on the
hand-built case (right corridor, wrong alcove) scores nothing.

## 8. Decisions we made, and what we turned down

| decision | why | what we didn't do |
|---|---|---|
| Repair levels rather than generate safe ones | There's a technique that generates only-completable levels by construction. It's genuinely good, and it can't repair a level someone already built | Constraint-based generation |
| Use the room graphs, not the picture data | The graphs are already machine-readable; the images would be a parsing project with no benefit | Parsing the tile maps |
| Use all three Zelda games | Boss keys and switches only appear in two of them. Using just the first game leaves that logic untested | Just the 18 original dungeons |
| Only test on the 31 that verify | The other 7 have transcription errors. Breaking an already-broken level gives you no meaningful right answer | Using all 38 |
| Solver decides, agent chooses | We measured it: the script fixes 100% for free. An agent doing that job would just lose | Agent proposes fixes and retries |
| Try least-destructive fixes first | Makes the script we're competing against as strong as we can honestly make it | An order that made our results look better |
| Break levels deliberately to get right answers | Turns opinion into measurement | AI-as-judge, or human ratings |
| Exact match scoring | Nobody can argue with it | Partial credit, which sneaks opinion back in |
| Give the agent tools, not a giant list | The biggest case has 612 options. The useful questions are comparative, not "what are they all?" | Dumping every option into the prompt |
| Route through a model-agnostic library | Anyone rerunning this can use whatever provider they have | Tying it to one provider |
| Take prices from that library | One source, updated with the library, can't drift | A price table we maintain by hand (we had one; deleted it) |
| Record everything as it happens | The recordings are a deliverable. Reconstructing them afterwards isn't evidence | Parsing logs after the fact |
| Ask a human before applying | Required for anything with real consequences, costs one line of code | Applying automatically |

## 9. What actually happened

| method | completable | recovered intent | layout kept | time | cost |
|---|---|---|---|---|---|
| roll a fresh dungeon | 77/77 | 0/77 (0%) | 0.034 | instant | free |
| ask a model once, no tools | **61/77** | 23/77 (29.9%) | 0.961 | 30s | $0.0035 |
| script, first fix that works | 77/77 | 26/77 (33.8%) | 0.965 | 0.06s | free |
| **the agent** | **77/77** | **34/77 (44.2%)** | 0.966 | 27s | $0.0051 |

The agent beats the best baseline by eight levels and never ships something
broken. The whole run costs about 65 cents.

**One important caveat on that headline.** The agent isn't deterministic, and as
mentioned earlier we can't make it so. We've now run it seven times end to end
and scored **32, 34, 34, 34, 34, 35 and 36 out of 77**. So the real figure is
somewhere around 42–47%, not a precise 44.2%. The script we're comparing against
is perfectly deterministic at 26/77, so the agent wins by six to ten levels every
time — that part isn't in doubt — but its own score wobbles by up to four.

**Look closely at the "ask a model once" row.** Its 29.9% looks nearly as good
as the script's 33.8%. It isn't, because **16 of its 77 answers leave the
dungeon impossible to finish.** That row is the single best argument in this
project for never reading "did it recover intent" without also checking "does it
still work."

### The win is narrower than it looks

| kind of damage | script | agent |
|---|---|---|
| misplaced key | 0/15 | **1/15** |
| missing corridor | 1/31 | **9/31** |
| wrong lock | 25/31 | **24/31** |

Almost the entire advantage comes from missing corridors, where "how far apart
are these rooms" is a genuinely useful signal and the agent goes from 1 to 9. On
wrong locks it's level with the script. And on misplaced keys — the exact
failure this whole project opens with — it gets one.

### Chasing the failure

The first thing we noticed: on 13 of 15 misplaced-key cases, the agent didn't
pick the wrong room to put the key back in. **It didn't try to move the key at
all.** It unlocked a door instead. That balances the number of keys against the
number of locks, it passes the check, and it's wrong — the dungeon now has one
fewer locked door than the designer drew, and the key is still in the wrong
place.

**Our first explanation was wrong, and checking it mattered.** We assumed the
diagnosis was burying the evidence. It wasn't. On a real case it reads:

```
goal room 5 is not reachable; small key(s) in room(s) 24, 25, 30 cannot
be collected; out of keys at door(s) 20-18; ...
```

The stranded keys are mentioned *first*, before the door list. The bug is named
in plain language at the front, and the agent walks straight past it.

But three genuine biases did exist, and all three were ours:

1. The list of available fixes came back in our "least destructive first" order,
   which puts unlocking at the top — and it **cut off after 25 entries**. On
   many levels the agent never saw any other kind of fix at all.
2. Our instructions used "unlocking a door that shouldn't be locked" as the very
   first example of a good repair.
3. Unlocking removes **every** requirement on a door, not just a key lock, and
   nothing told the agent that. Nine of its 48 unlocks demolished deliberate
   structure — seven solid walls, a boss door, an item gate.

### Experiment one: fix the biases

We rebalanced the list so it samples evenly across kinds, reworded the
instructions, and added a warning whenever unlocking would destroy something
other than a key lock.

Unlocking dropped from 48 choices to 40, exactly as intended. The score went
from 34/77 to 34/77. Four cases got better, four got worse.

At the time we read a lot into *which* four. Hold that thought.

### Experiment two: make it commit first

Maybe the problem was that the agent never had to form an opinion — the list of
fixes was available immediately, so it could browse first and think later.

So we locked the fix tools until it committed to a diagnosis. It has to state
what kind of bug it thinks happened, and which rooms are involved, before it can
see any options. It's allowed to change its mind afterwards, but we score the
first guess.

It scored **31/77** — worse. But it bought us something much more valuable: a
second, independent measurement.

```
guessed the right kind of bug:                 59/77 = 76.6%
  of those, produced the exact right fix:      31     = 53%
  of the 18 wrong guesses, right fix anyway:    0     =  0%
```

**The agent works out what's wrong about twice as often as it works out how to
fix it.** The 28 cases where it diagnosed correctly and then repaired wrongly
are the real problem, and they aren't a diagnosis problem at all.

On the hand-built case it wrote this before seeing a single option: *"the
failure is a circular key dependency: rooms 10 and 11 provide the first two
keys, but the third small key and boss key are in room 13, beyond the gate."*
That's correct and precise. Then it proposed removing the gate rather than
moving the key. It diagnosed a stranded key and prescribed demolition.

Also notable: a wrong diagnosis is fatal, 18 times out of 18. And forcing it to
commit removed a lucky path — without the gate, the agent could occasionally
stumble onto the right answer without having reasoned to it. **The version that
thinks more carefully scores worse.**

### Experiment three: the one we should have run first

Three experiments in, we finally ran the obvious control: the same setup against
itself, changing absolutely nothing.

| comparison | what changed | score | cases that flipped | same fix chosen |
|---|---|---|---|---|
| run vs. rerun | **nothing** | 34 → 32 | **8** | 49/77 |
| before vs. after rebalancing | the fix list | 34 → 34 | 8 | 46/77 |
| before vs. after forced diagnosis | the gate | 34 → 31 | 17 | 36/77 |

**Given the exact same question twice, the agent picks the same fix only 64% of
the time.** Changing nothing at all flips eight cases.

Eight. Which is exactly how many the rebalancing experiment flipped.

So everything we inferred from *which* four cases got better and which four got
worse was reading patterns in the model's own randomness. That conclusion is
gone, and we've marked it as retracted in the changelog rather than quietly
deleting it, because it's the most useful mistake in the project.

What *did* survive, because it reproduces: the rerun chose 41 unlocks against
the previous run's 40, nowhere near the original 48. So **changing the tools
reliably changes what the agent reaches for, and reliably fails to change how
often it's right.** You can steer an agent far more easily than you can improve
it.

### Experiment four: give it what it was missing

Section 10 used to say the obvious next move was to show the agent the
dungeon's rhythm, because working out which room a key came from means
recognising a pattern and none of our tools expose patterns. So we built it,
and we built the other half too — a way to tell the agent what the shape of the
verified list rules out.

First surprise: **the rhythm we'd assumed isn't there.** We'd said dungeons put
an alcove before every gate, so a stray key belongs in the alcove in front of
the lock it opens. Measured across the corpus, 102 of 127 keys sit *beyond*
their nearest locked door, not in front of it. The story was wrong. What's
actually true is duller — keys go in rooms with enemies, and in dead ends.

Second surprise: those motifs **narrow but don't rank**. "The home room has an
enemy in it" throws away half the candidates and keeps the right one 13 times
out of 15, which sounds useful. But scoring rooms by all the motifs together
picks the right one twice out of fifteen — no better than plain topology. So we
shipped it as evidence for the agent to weigh, not as an ordering.

Then we ran it. Five times.

| run | total | the 23 "one legal unlock" cases | everything else |
|---|---|---|---|
| baseline | 34 | 18 | 16 |
| baseline again | 32 | 19 | 13 |
| with memory and both notes | 35 | **21** | 14 |
| again | 34 | **21** | 13 |
| memory restricted to key cases | 34 | **21** | 13 |
| one note removed | 36 | **21** | 15 |
| again | 34 | **21** | 13 |

One column reproduces and the rest is weather. Twenty-one out of twenty-three
is the *ceiling* of that rule — the other two are displaced keys it mislabels —
and the agent hits the ceiling every single time once you tell it the fact.
The total doesn't move: 34.6 on average against 33, well inside the eight-case
wobble from the last experiment.

We wrote down two predictions before running and got both wrong. First we
thought the memory was distracting the agent on corridor cases, so we stopped
offering it there; corridors didn't recover. Then we thought a second note —
"this must be a dropped corridor" — was the culprit, so we removed it; one run
said yes (36), the repeat said no (34). Both stories died.

What survives is a sharper version of experiment one's lesson:

> **The agent converts facts and ignores hints.** Tell it something that closes
> the question and it acts on it, reliably, up to the limit of what the fact
> supports. Tell it a tendency measured at lift 1.45 and nothing happens. Tell
> it something true that merely narrows — "this must be a corridor" — and
> nothing happens either.

That's worth more than three cases. It says the way to improve this agent is
not better hints, richer context or more persuasive instructions. It's finding
more places where the machinery around it can settle a question outright, and
handing those over as facts.

### What we'd tell you to do differently

1. **Run the do-nothing comparison first.** Not fifth. Until you know how much
   your agent disagrees with itself, an A/B test on 77 cases can't detect
   anything smaller than about eight cases — and every single flipped case will
   still have a convincing story you can tell about it.
2. **Watch the distribution, not just the score.** The mix of choices moved
   reliably. The score never did. Those are different findings and only one of
   them was real.
3. **Measure the middle step.** The gap between 76.6% diagnosis and 40.3% repair
   is completely invisible if you only score the final answer.
4. **Write the prediction down before the run.** We did this for the last two
   experiments and both predictions were wrong — which we only know for certain
   because they were written down first. Deciding afterwards what the result
   meant would have produced two confident, plausible, unfalsifiable stories.
5. **Score subsets, not just totals.** The last experiment's total moved by one
   case and looked like nothing. Split by which cases the change could possibly
   affect, it was a clean +3 that reproduced five times running, cancelled by
   noise elsewhere. The total was hiding both halves.

## 10. Where we'd take it next

**Find more facts, not more hints.** This used to say "show the agent the
dungeon's rhythm". We did, and section 9 records how that went: the motifs are
real, weak, and the agent ignores them. The thing that *did* work was telling
it something the verified list already determined. So the productive direction
is auditing the pipeline for other places where the machinery can settle a
question outright — and there may not be many, which is itself the finding.

**Give rooms real positions — but know what it buys.** The dataset records what
connects to what, not where anything is. We tried to recover the geometry from
the tile maps that ship alongside the graphs; they turn out to be a different
transcription that disagrees on room count in 17 of 18 dungeons, so that door is
closed (see [docs/DATA_NOTES.md](docs/DATA_NOTES.md)).

We then built coordinate-carrying dungeons from scratch to find out what
geometry would actually be worth. Requiring a corridor to join physically
adjacent rooms cuts the candidates from 73 to about 4 while never losing the
right one — a sixteen-fold narrowing. And a uniform pick among those four is
still 25%. Geometry roughly triples the odds and leaves a judgment call. Worth
having, not a solution, and the honest caveat still stands: it would make the
scripted baselines better too.

**Handle more than one thing being broken.** Right now we break one thing and
fix one thing. Two simultaneous faults would need a different approach, because
trying every *pair* of edits explodes combinatorially — which is exactly where
an agent proposing candidate pairs would genuinely earn its keep.

**Support new mechanics.** Adding a new kind of lock currently means writing new
solver rules by hand. Letting the agent extend the solver, with the 31-dungeon
test as a safety net, is the natural stretch goal.

**Give partial credit.** Exact match scores the hand-built near-miss (right
corridor, wrong alcove) as zero. A distance-weighted second metric would show
progress more fairly — reported *alongside* exact match, never replacing it.

## 11. Where to learn this properly

I've given titles and authors rather than links or reference numbers, on
purpose: look them up rather than trusting an identifier written from memory.

### Generated content in games, generally

- ***Procedural Content Generation in Games*** — Shaker, Togelius & Nelson. The
  standard textbook, and it's **free at pcgbook.com**. Start here.
- **"Search-Based Procedural Content Generation: A Taxonomy and Survey"** —
  Togelius, Yannakakis, Stanley & Browne (2011). The framing most of the field
  still uses.
- **"Procedural Content Generation via Machine Learning"** — Summerville and
  others (2018). The survey, and the work that motivated the dataset we use.

### The dataset

- **"The VGLC: The Video Game Level Corpus"** — Summerville, Snodgrass, Mateas
  & Ontañón (2016). Available at **github.com/TheVGLC/TheVGLC**.

### Key-and-lock dungeons specifically

A smaller field than you'd expect.

- **"Adventures in Level Design: Generating Missions and Spaces for Action
  Adventure Games"** — Joris Dormans (2010). Separates the *sequence of things
  you do* from the *space you do them in*, which underpins most Zelda-style
  generation. **The most relevant single paper to this project.**
- **"Generating Missions and Spaces for Adaptable Play Experiences"** — Dormans
  & Bakkes (2011).
- **Game randomizer communities.** The people who build randomizers for Zelda
  games have spent a decade writing exactly the kind of "what can you reach given
  what you're carrying" solver that our `solver.py` is a small version of. Their
  open-source logic code is the best practical resource on this problem and is
  almost entirely unpublished academically.

### The approach we didn't take

- **"Answer Set Programming for Procedural Content Generation"** — Adam Smith &
  Michael Mateas (2011). The technique that generates only-valid levels by
  construction. Genuinely stronger than ours *for generating*; it just can't
  repair something that already exists.
- **Potassco / clingo** at **potassco.org** — the toolchain you'd actually use.
- **Sturgeon** — Seth Cooper's constraint-based level generator. Modern,
  practical, actively maintained.

### Search

- ***Artificial Intelligence: A Modern Approach*** — Russell & Norvig, chapters
  3 and 4. Our solver is a breadth-first search over a compound state, and this
  is the material that explains why that's the right shape for the problem.
- **Bit-pattern state encoding** — the trick that makes it fast. Any
  competitive-programming write-up of "bitmask dynamic programming" covers it;
  **cp-algorithms.com** is a good free reference.
- **Classical planning and PDDL** — the fully general version of "what can I
  reach given resources I use up." Worth knowing it exists; overkill here.

### Automatically fixing broken things — read this section

Structurally, this project is automated program repair applied to game levels.
That field discovered our exact failure mode years ago and gave it a name.

- **"Automatic Software Repair: A Bibliography"** — Martin Monperrus (2018). The
  map of the territory.
- **"GenProg: A Generic Method for Automatic Software Repair"** — Le Goues,
  Nguyen, Forrest & Weimer (2012). Generate lots of candidate fixes, test each
  one — the same shape as our fix generator.
- **"Is the Cure Worse Than the Disease? Overfitting in Automated Program
  Repair"** — Smith, Barr, Le Goues & Brun (2015). **If you read one thing from
  this list, read this.** It's our headline finding, a decade earlier, in
  software: patches that pass every test and are still wrong. Their "overfitting
  to the test suite" is our "passes the check and is still a teleporter."

### Where our measurement method comes from

- **"An Analysis and Survey of the Development of Mutation Testing"** — Jia &
  Harman (2011). Deliberately injected faults with known fixes, which is exactly
  what `corrupt.py` does.

### Building agents

- **"Building Effective Agents"** — Anthropic's engineering blog (2024). The
  clearest short piece on when you *don't* need an agent, which is the decision
  this entire architecture rests on.
- **Anthropic's writing on designing tools for agents.** Tool design as the main
  lever — directly relevant to our section 9.
- **"ReAct: Synergizing Reasoning and Acting in Language Models"** — Yao and
  others (2022). The think/act/observe loop our agent implements.
- **"Let's Verify Step by Step"** — Lightman and others (2023). Letting a checker
  settle correctness so the model can spend its effort elsewhere — the general
  form of our whole design.
- **"Judging LLM-as-a-Judge"** — Zheng and others (2023). Useful mainly for
  understanding what we dodged by manufacturing our own right answers.

### The tools we used

- **litellm** at **docs.litellm.ai** — provider routing, pricing, retries.
- **pytest** at **docs.pytest.org** — particularly fixtures, which are how we
  test the agent without needing an API key.
- **The Graphviz DOT language** at **graphviz.org** — what the dungeon files
  actually are.

## 12. Glossary

| term | what it means here |
|---|---|
| **case** | one broken level, plus a record of the change that broke it |
| **candidate** | a single fix the solver has confirmed makes the level completable |
| **intent recovery** | the fix chosen exactly matches undoing the change we made |
| **layout preservation** | how much of the original dungeon survived, from 0 to 1 |
| **soft lock** | a door label in the dataset that, despite the name, you *can* walk through |
| **key economy** | how the number of keys placed relates to the number of locked doors on the route |
| **blocker** | a door you can reach but never get through, and the reason why |
| **the gate** | the completability check — necessary, and nowhere near sufficient |
